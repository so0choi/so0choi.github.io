# 글 유형별 뼈대

리뷰할 때 글 유형을 먼저 정하고 아래 뼈대와 비교한다. 뼈대는 정답이 아니라 독자가 기대하는 순서다. 다르게 썼다면 그럴 만한 이유가 있는지 본다.

## 트러블슈팅

독자는 같은 에러를 검색해서 들어온다. 해결책을 찾을 때까지 스크롤을 오래 참지 않는다.

1. **증상**: 에러 메시지 원문(코드 블록), 어떤 환경에서 났는지. 검색어가 되는 부분이라 맨 위에 있어야 한다.
2. **한 줄 요약**: 원인은 X, 해결은 Y. 바쁜 독자는 여기서 떠나도 된다.
3. **원인**: 왜 이 에러가 났는지. 시도했다가 실패한 방법은 짧게(같은 길을 가는 독자를 아껴 준다).
4. **해결**: 따라 할 수 있는 단계와 코드. 선택지가 여럿이면 각각의 장단점.
5. **확인 방법**: 해결됐는지 어떻게 알 수 있는지.
6. **참고**: 공식 문서, 이슈 링크.

자주 보이는 문제: 시간 순서대로 삽질 과정을 다 쓰고 해결책이 맨 끝에 나온다. 삽질 기록 자체가 가치 있는 글(예: 여러 원인이 겹친 경우)이라면 각 시도를 소제목으로 나누고, 맨 위에 최종 원인을 먼저 밝힌다.

## 회고 / 후기

독자는 "이 사람이 무엇을 배웠나"를 얻으러 온다. 일기와의 차이는 교훈이 앞에 있다는 것이다.

1. **요약**: 무엇을 했고, 결과는 어땠고(숫자), 가장 큰 교훈은 무엇인지 3~5줄.
2. **맥락**: 무엇을 왜 했는지. 독자가 상황을 이해할 만큼만.
3. **한 일**: 만든 것, 결정한 것과 그 이유.
4. **결과**: 숫자, 잘된 것과 무너진 것.
5. **회고**: 왜 그렇게 됐는지, 다시 한다면 무엇을 바꿀지. 소제목에 교훈을 문장으로 쓴다(예: "질문 절반이 헛돌았다").

자주 보이는 문제: "결론은 글 끝에서"처럼 요점을 미룬다. 회고 소제목이 "아쉬운 점"처럼 내용을 말하지 않는다.

## 개념 정리 / 비교

이미 같은 주제의 글이 많아서, 이 글만의 관점이 없으면 읽힐 이유가 없다.

1. **왜 이걸 정리하는가**: 실무에서 어떤 상황에 부딪혀서 찾아봤는지. 이게 다른 글과의 차별점이 된다.
2. **한 문장 정의**: 개념을 한 문장으로.
3. **동작 방식**: 그림이나 최소한의 예제 코드.
4. **비교 / 언제 쓰나**: 비슷한 것과의 차이를 표로. 선택 기준.
5. **실무에서 주의할 점**: 직접 겪은 것이 있으면 반드시 넣는다.

자주 보이는 문제: 공식 문서를 순서대로 옮겨 적는다. 제목이 "X 알아보기"라 검색 의도(X vs Y, X 사용법, X 에러)와 맞지 않는다.

## 튜토리얼 / 구축기

독자는 따라 하려고 온다. 빠진 단계가 하나라도 있으면 막힌다.

1. **목표와 결과물**: 끝나면 무엇이 되는지, 최종 구조(그림이나 흐름).
2. **전제 조건**: 버전, 계정, 권한, 미리 설치할 것.
3. **단계**: 번호가 있는 소제목. 각 단계는 "무엇을 → 왜 → 코드/설정 → 확인".
4. **전체 설정 파일**: 마지막에 한 번에 복사할 수 있게.
5. **대안과 한계**: 다른 방법을 안 쓴 이유, 남은 과제.

자주 보이는 문제: 콘솔 스크린샷만 있고 무엇을 입력했는지 글로 없다. 왜 그 설정값인지 설명이 없다.

## 공통: 제목과 description

- 제목에는 사람들이 실제로 검색할 말을 넣는다. 에러 메시지의 핵심 단어, 기술명, 하려는 일. "X 알아보기"보다 "X로 Y 하기", "X 에러 해결".
- description은 검색 결과 아래 2줄로 보인다. 제목을 반복하지 말고 "무엇을, 어떻게 해결/정리했는지"를 1~2문장으로.
